# Backend — Kelola Gudang Pro

Laravel 13 API (`/api`) powering the master data module (Kategori, Sub Kategori, Merk, Satuan, Gudang, Rak, Bin, Supplier, Customer, Vendor, Barang, Departemen, Proyek, Work Order) and the Persediaan module (Stock Saat Ini, Kartu Stock, Mutasi Stock). The frontend (`Frontend/`) calls this API for those pages; the rest of the app is still UI-only dummy data.

## Stack & environment

- PHP ^8.3 (Laragon), Laravel 13.24.
- **PostgreSQL 18** at `127.0.0.1:5432`, user `postgres` / password `postgres`.
  - NOT on PATH — use full path `C:/Program Files/PostgreSQL/18/bin/psql.exe` / `createdb.exe`.
  - Dev DB `kelolagudang`, test DB `kelolagudang_test` (defined in `phpunit.xml`).
  - First-time: `CREATE DATABASE kelolagudang; CREATE DATABASE kelolagudang_test;` via psql (do this before `migrate`/`setup`).
- `.npmrc` sets `ignore-scripts=true` — npm deps never run postinstall scripts.
- `laravel/boost` is NOT installed (README mentions it; ignore).

## API conventions

- Routes live in `routes/api.php` (registered via `withRouting(api: ...)` in `bootstrap/app.php`).
- **Auth is Sanctum bearer-token** (no session/CSRF): `POST /api/auth/login` (`AuthController@login`, middleware `throttle:5,1`) checks credentials + `is_active`, issues a personal access token via `createToken('kg-session')`, and returns `{ data, access, token }` (`access` = the user's `role_permissions` map). `GET /api/auth/me` and `POST /api/auth/logout` are `auth:sanctum`; logout deletes the current token. `statefulApi()` is **not** enabled — the SPA authenticates with `Authorization: Bearer <plainTextToken>`, so there is no cookie flow, no `/sanctum/csrf-cookie`, no `X-XSRF-TOKEN`, and no `ConfigureCrossSiteCookie` middleware.
- **RBAC**: `/api/master/*` runs `['auth:sanctum', 'role.access:Master Data']` and `/api/persediaan/*` runs `['auth:sanctum', 'role.access:Persediaan']` — `EnsureRoleAccess` (alias `role.access`) derives the required level from the HTTP verb (GET/HEAD=`Baca`, POST/PUT/PATCH=`Tulis`, DELETE=`Kelola`) and 403s when the role lacks that `(module, level)`. Missing rows = no access. Note the frontend "Transaksi → Barang Masuk/Keluar/Transfer Gudang/Retur Pembelian/Retur Penjualan" forms post to `POST /api/persediaan/stock-documents` (`Penerimaan`/`Pengeluaran`/`Transfer Gudang`/`Retur Pembelian`/`Retur Penjualan`; Transfer Gudang mengirim `destination_warehouse_id` dan memosting pasangan OUT+IN; Retur Pembelian = OUT ke supplier dengan nomor `RP` (opsional merujuk dokumen Penerimaan sumber via `source_document_id` + `source_line_id` per baris — harga beli asal, cap sisa qty), Retur Penjualan = IN dari customer dengan nomor `RJ` (opsional merujuk dokumen Pengeluaran sumber via `source_document_id` + `source_line_id` per baris — harga baris BK & bin kembali, cap sisa qty)), so creating them needs `Persediaan` **Tulis** even though the menu lives under the `Transaksi` module (all seeded roles carry both).
- Controllers follow `apiResource` style: `index` (list), `store`, `show`, `update`, `destroy`.
- **Non-`apiResource` extras** on `items`: `POST /api/master/items/bulk-delete` and `POST /api/master/items/bulk-status` (`ItemController::bulkDestroy` / `bulkUpdateStatus`, validated by `BulkItemDeleteRequest` / `BulkItemStatusRequest`).
- `index` supports `search`, per-entity filters, and `per_page`. Responses use Laravel's default envelope: `{ data }` for single, `{ data, links, meta }` for paginated collections.
- Resources serialize to match the frontend shapes (`src/lib/master-types.ts`); e.g. ItemResource maps `min_stock→min`, `max_stock→max`, `lead_time→leadTime`, relation names→`category`/`subCategory`. It also exposes raw `category_id`/`sub_category_id` so the edit form can prefill selects. Fields for not-yet-built relations return `null`.
- The frontend proxies `/api` → `http://127.0.0.1:8000` in dev (see `Frontend/vite.config.ts`), so both servers must run: `composer dev` (this dir) + `npm run dev` (in `Frontend/`).
- Validation in `app/Http/Requests` (FormRequests); `code`/`sku`/`barcode` are unique with `Rule::unique(...)->ignore()` on update.
- CORS is enabled via `config/cors.php` (`allowed_origins: *`, `supports_credentials: false`, `paths: ['api/*']`). Because auth is bearer-token based (no cookie credentials), CORS only matters for the rare direct cross-origin call — the deployed frontend hits the API same-origin through the Vercel proxy (`Frontend/vercel.json`) in production and the Vite proxy in dev.
- Deleting a category that still has sub-categories/items, a rack with bins/items, a bin with items, a warehouse with racks/items, a supplier still referenced by items, or a project still referenced by work orders is blocked (422). Deleting an **item** referenced by a work order is also blocked (422) — `ItemController::destroy`/`bulkDestroy` guards on `items`→`work_orders` (`restrictOnDelete`).
- **`users` is full `apiResource` CRUD** (store/update/destroy added on top of the original read-only index): `GET /api/master/users` (index with `search` over name/email/code), `POST`, `GET /{id}`, `PUT /{id}`, `DELETE /{id}`. Users carry `code` (`USR-###`, auto-generated via `CodeGenerator` when omitted), `role` (`Rule::in(['Administrator','Supervisor','Operator Gudang','Auditor'])`), and `is_active`. Passwords are `required|min:8|max:64|confirmed` on store, `nullable` on update (blank = unchanged); hashed via the model's `hashed` cast. Deleting a user nulls their `head_user_id`/`pic_user_id` references (`nullOnDelete`) — prefer toggling `is_active` off for offboarding. `/api/master/departments`, `/api/master/projects`, `/api/master/work-orders` are full `apiResource` CRUD.
- **`GET /api/master/roles`** (`RoleController@index`) catalogs the 4 user roles derived from `StoreUserRequest::ROLES`, each with `id` (1–4, enum order), `user_count` (total users with that role), `active_user_count` (where `is_active` is true), and `access` (per-role module→level mapping from `role_permissions`). **`PUT /api/master/roles/{role}`** (`RoleController@update`, `UpdateRoleRequest`) replaces that role's access wholesale (delete + reinsert in a transaction; `access` must be an array of `{ module, level }` — `module` in `RolePermission::MODULES`, `level` in `RolePermission::LEVELS`, modules unique; empty array = no access). Roles are a validated string enum on `users.role` — there is no `roles` table and role names are not editable. RBAC is enforced at runtime by `EnsureRoleAccess` (`role.access`, see the auth note above) against this map; empty array = the role has no module rows at all. Seeded by `RolePermissionSeeder`.
- **Persediaan API** (mounted under `/api/persediaan`, middleware `['auth:sanctum', 'role.access:Persediaan']`): `GET /stock` (Stock Saat Ini, `StockController@index`), `GET /stock-card` (Kartu Stock dengan metode penilaian FIFO/Average/Maximum Cost, `stockCard`), `GET /stock-minimum` (Stock Minimum, `StockController@stockMinimum`), `GET /valuation` (Nilai Persediaan, `StockController@valuation`), and `stock-documents` (`StockDocumentController`):
  - `GET /valuation` — satu baris per item: nilai on-hand di bawah tiap metode penilaian (`nilai_fifo`, `nilai_avg`, `nilai_max` + `unit_cost_*` masing-masing), difold dari ledger `stock_movements` persis seperti Kartu Stock; plus `stock` (saldo hasil fold), `reserved`, `available`, dan klasifikasi `moving` (`Fast` ≤20 hari, `Medium` ≤60, `Slow` ≤150, `Dead` >150 sejak `last_move_at`; item tanpa movement = `Dead`). Filters: `warehouse_id`, `category_id`, `search`, `per_page`. Nilai dihitung dari unit cost yang sudah dibulatkan (konsisten: `nilai = stock × unit_cost`).
  - `GET /stock-minimum` — satu baris per item: `min`, `max`, `stock`, `available`, `avg_daily_usage` (konsumsi 30/60/90 hari ⇒ `/30` (default) | `/60` | `/90`), `days_of_cover` (stock ÷ ADU, null bila ADU=0), `status` (`Habis` stock≤0, `Kritis` 0<stock≤min, `Menipis` min<stock≤max, `Normal` — prioritas status tertinggi), `suggested_qty` (max − available, ramp minimum `max`), plus `warehouse`/`category`. Filters: `warehouse_id`, `category_id`, `days` (3/30/60, default 30, dipakai untuk ADU), `search` (sku/nama), `status`, `per_page`, `sort_by`, `order`.
  - `GET /stock-documents` — daftar dokumen mutasi, filter `search` (no/partner/note), `type`, `status`, `warehouse_id`, `from`/`to`, `per_page`; order `document_date` desc; eager `warehouse`/`destination` + `line_count`.
  - `GET /stock-documents/{stockDocument}` — detail + `lines` (item sku/name/unit, qty/system/actual, variance, from/to bin) + `movements` tidak disertakan (lihat kartu stock).
  - `POST /stock-documents/{stockDocument}/post` — posting Draft/Menunggu Approval via `StockDocumentService`; idempotent (sudah Selesai = no-op); 422 bila Dibatalkan atau stok tak cukup.
  - `POST /stock-documents/{stockDocument}/cancel` — Draft/Menunggu Approval → Dibatalkan; 422 bila sudah posting.
  - `StockDocumentResource` menyerialkan `no`, `type`, `status`, `document_date`, `warehouse`/`destination` (name + raw FK), `partner`, `reference_no`, `pic`, `note`, `posted_at`, `created_by`, `line_count` (whenCounted), `lines` (whenLoaded).
- Resources for relation fields use the **string-name + raw FK** pattern (like `ItemResource`): e.g. `head`/`pic`/`project`/`item`/`unit` render the related record's `name`/`code` via `whenLoaded(fn () => $this->project?->name)`, and raw FKs (`head_user_id`, `pic_user_id`, `project_id`, `item_id`, `unit_id`) are exposed for form prefill. `ProjectResource` also exposes `work_orders_count` via `whenCounted`.

## Schema notes

- `role_permissions` stores the module→level access map (`role`, `module`, `level`, unique `(role, module)`). `role` is a plain string (enum values from `StoreUserRequest::ROLES` — no FK since there's no `roles` table), `module` ∈ `RolePermission::MODULES`, `level` ∈ `RolePermission::LEVELS`. Missing `(role, module)` rows mean "no access". Seeded by `RolePermissionSeeder` (mirrors the old static `ROLE_ACCESS` in `Frontend/src/lib/schemas.ts`, with Auditor's "Semua Modul" expanded to explicit per-module rows).
- `items.stock`/`items.reserved` are denormalized projections; the source of truth is the movement ledger. `item_stock` (composite PK `item_id, warehouse_id, bin_id`) stores per-location `stock`, `reserved`, `unit_cost_avg` — rebuilt by `StockLedger::rebuildForItem` (folds `stock_movements`) and `setReserved` (weighted distribution; item total derived from per-bin sums so `items.reserved == SUM(item_stock.reserved)`). The Persediaan module (Stock Saat Ini, Kartu Stock) reads these.
- **Mutasi Stock (`StockDocumentSeeder`)** seeds `stock_documents` → `stock_document_lines` → `stock_movements` (deterministic LCG PRNG, ref date `2026-08-01`):
  - `stock_documents`: `no` UK (`BM/BK/RP/RJ/ADJ/TF/SO/YYYY/#####`), `type` ∈ `StockDocument::TYPES` (including `Retur Pembelian`/`Retur Penjualan`), `status` ∈ `StockDocument::STATUSES` (seeded `Selesai` = posted, plus a handful Draft/Menunggu Approval/Dibatalkan), `document_date`, `warehouse_id`/`destination_warehouse_id`→warehouses `nullOnDelete`, `source_document_id`→stock_documents `nullOnDelete` (Retur Pembelian → dokumen Penerimaan sumber, Retur Penjualan → dokumen Pengeluaran sumber), `partner`, `reference_no` (`PO-####`/`SPK-####`), `pic`, `note`, `posted_at` (set hanya untuk `Selesai`).
  - `stock_document_lines`: `document_id` FK → `stock_documents` (`cascadeOnDelete`; unique `(document_id, line_no)`), `item_id` → items `restrictOnDelete`, `qty` signed (BM/BK/ADJ/TF positif = masuk), `system_qty`/`actual_qty` untuk Stock Opname (variance = actual - system), `from_bin_id`/`to_bin_id` → bins `nullOnDelete`, `source_line_id` → stock_document_lines `nullOnDelete` (baris Penerimaan sumber untuk baris retur ter-link), `unit_cost`, `note`.
  - `stock_movements` gained `stock_document_id` (FK, `nullOnDelete`), `line_no`, `pair_id` (self-FK) — Transfer Gudang writes an OUT + IN mirror pair linked via `pair_id`. Line helper `moveQty()`/`moveDirection()` derive movement from line (opname uses |actual-system|).
  - Posting a document is orchestrated by `StockDocumentService` (derive 1–2 movement payloads per line, assert non-negative stock on OUT via `item_stock` available, rebuild ledger, mark Selesai). Seeded posted documents feed the existing Stock Saat Ini / Kartu Stock data.
  - **Opname → koreksi (Draft-then-post)**: dokumen Stock Opname tidak memindahkan stok (0 movement). Saat opname diselesaikan, `StockDocumentService::postOpname` membuat dokumen Stock Adjustment **Draft** (`ADJ`, `source_document_id` → opname, `reason_code` diwarisi dari baris opname) dan **TIDAK langsung memostingnya** — stok belum berubah. Posting koreksi dilakukan belakangan dari halaman Penyesuaian (frontend `persediaan.adjustment` → tombol Posting/Batalkan di `stock-document-sheet`), barulah ledger bergeser. Guard stok fisik untuk ADJ ter-link opname tetap berlaku di posting tersebut.
- `items.brand_id` has an FK to `merks` (nullable, `nullOnDelete`), `unit_id` to `units`, `default_warehouse_id` to `warehouses` (both nullable, `nullOnDelete`). `default_rack_id`/`default_bin_id` are FKs to `racks`/`bins` (nullable, `nullOnDelete`). `preferred_supplier_id` is an FK to `suppliers` (nullable, `nullOnDelete`) and resolves to the supplier `name` via ItemResource `supplier` when loaded.
- `racks` belongsTo `warehouses` (`cascadeOnDelete`) and hasMany `bins` (`cascadeOnDelete`) / `items` via `default_rack_id`. `bins` hasMany `items` via `default_bin_id`. `suppliers` hasMany `items` via `preferred_supplier_id`. Codes auto-generate via `CodeGenerator` (`RAK-###`, `BIN-###`, `SUP-###`, `CUS-###`, `VDR-###`) when omitted. Rack/bins codes are built from location components: racks `{aisle}-{bay}` (e.g. `A-01`), bins `{level}-{position}`. Rack `name` is optional — `RackController` auto-fills `Rak {code}` (e.g. `Rak A-01`) when omitted; the code is the canonical physical-address identity, `name` is a descriptive label.
- Item belongsTo Category (required), SubCategory (nullable), and Supplier (nullable). SubCategory belongsTo Category (cascade delete).
- `payment_terms` (suppliers) is `Rule::in(['NET 30','NET 14','COD','NET 45'])`, `segment` (customers) is `Rule::in(['Retail','Distributor','Proyek','Korporat'])`, `service_type` (vendors) is `Rule::in(['Ekspedisi','Maintenance','Kalibrasi','Cleaning'])` — all nullable.
- Supplier/Customer/Vendor carry "detail PT" fields: `legal_name`, `nib` (13 digits), `npwp` (validated via `App\Rules\ValidNpwp`, backed by `App\Support\Npwp` — Luhn checksum on the leading digits, see `tests/Unit/NpwpTest.php`), `pic_name`, `website`, bank info (`bank_name`/`bank_account_no`/`bank_account_name`). (A `verification_status`/`verification_note`/`verified_at` workflow existed but was removed — verification is a purchasing/AP concern, not warehouse.)
- `departments` (code `DEP-###` UK, name UK, `head_user_id`→users `nullOnDelete`, `is_active`), `projects` (code `PRJ-###` UK, name UK, `pic_user_id`→users `nullOnDelete`, `start_date`/`end_date` nullable, `status` `Rule::in(['Perencanaan','Berjalan','Selesai'])`, `budget` decimal(15,2) nullable), and `work_orders` (no `WO-###` UK, `project_id`→projects `cascadeOnDelete`, `item_id`→items **`restrictOnDelete`**, `unit_id`→units `nullOnDelete`, `target_qty` int, `start_date`/`finish_date` nullable, `pic_user_id`→users `nullOnDelete`, `status` `Rule::in(['Perencanaan','Berjalan','Selesai','Ditunda'])`). Codes auto-generate via `CodeGenerator` (`DEP-###`, `PRJ-###` via `next()`; `WO/YYYY/####` via `CodeGenerator::nextYearly()` — a per-year sequence under the current year's head `WO/{YEAR}/`). Seeders reference the 6 PIC users from `UserSeeder` (`Agus Salim`, `Bayu Pratama`, `Dewi Lestari`, `Nur Hidayat`, `Rudi Hartono`, `Siti Aminah`).
